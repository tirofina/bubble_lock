# R12 CSE Handover 및 서비스 연속성

실제 Mobius4 CSE 프로세스 두 개에서 위치, CSE 가용성, 지연, load 이벤트가 자동 handover 30회를 만들었고, 모의 키링 관측 2154건을 손실 0건, CSE 중복 0건으로 전달함.

- 실행 receipt: `docs/verification-evidence/2026-11-19/handover-auto-real-cse.json` (status PASS, runId `1795089224796_b5d7d1`)
- 실행 스크립트: `pc-mobius/scripts/run-handover-auto-real.mjs`
- 시험: `pc-mobius/test/handover-automation.test.mjs` 8건 PASS, `npm --prefix pc-mobius test` 163건 PASS

## 구성

| 항목 | 값 |
|---|---|
| 호스트 | 단일 Windows 물리 호스트, loopback HTTP |
| CSE | Mobius4 4.24.5 프로세스 2개(`/edge-a`, `/edge-b`), PostgreSQL 17 DB 각각 분리 |
| 지연 경로 | CSE마다 앞단 TCP 지연 proxy 프로세스, edge-a 기본 편도 0ms, edge-b 기본 편도 8ms(지역 Edge 가정), 주입 시 edge-a 편도 40ms |
| zone | home(edge-a 전용), street(두 Edge 공용), outside(edge-b 전용) 원형 geofence |
| 장치 | 모의 키링 telemetry 20Hz(50ms), Gateway telemetry 스키마 1.0.0, 37번째 sequence마다 재전송 1건 주입 |
| Gateway 경로 | 기존 `GatewayBridge`가 binarySwitch 최신 상태를 현재 소유 CSE에 PUT, `ObservationForwarder`가 sequence 관측을 CIN `obs-<sequence>`로 기록 |
| 구독 | `state-sub`(switch, net 1), `obs-sub`(observations, net 1과 3), 앱 callback이 sequence 기준 dedup 수행 |

트리거 경로는 다음과 같음. 실행 스크립트는 위치, 프로세스 종료와 재시작, 지연 주입, load 보고만 바꾸고 이동 결정은 coordinator 트리거가 내림.

| 종류 | 이벤트 원천 | 연결 경로 | 실행 정책 |
|---|---|---|---|
| zone | MEC Location 보고 250ms 주기(스크립트 위치) | `MecPolicyReconciler` 승인 zone 정책, `considerTrigger(kind: zone)` | 경계 안쪽 20m, dwell 500ms |
| availability | CSE base probe 100ms 주기, 실제 프로세스 종료(TerminateProcess) | `HandoverAutomation.probeEdge`, `considerTrigger(kind: availability)` | 연속 실패 3회, 체류와 cooldown 대신 실패 횟수로 판정 |
| performance | probe RTT EWMA(alpha 0.3)와 edge-agent load | `selectEligibleEdge` 점수(load + RTT/50ms), `considerTrigger(kind: performance)` | 점수 차 0.15 이상이 600ms 유지 |
| 공통 | 현재 grant revision, ownership epoch | 최소 체류 1.5s, cooldown 1.5s | 기본값은 기존 30s, 60s, 10s 유지 |

라운드 하나는 zone 이동 2회(home에서 outside, outside에서 home), edge-a 프로세스 종료 failover 1회, 재시작 뒤 성능 failback 1회, 지연 주입(홀수 라운드) 또는 load 0.7 보고(짝수 라운드) 이동 1회, 해제 뒤 failback 1회로 구성함. 5라운드를 실행함.

## 구현

- `pc-mobius/integration/src/handover-coordinator.mjs`: `DEFAULT_TRIGGER_POLICY`(기본값은 기존 상수와 같음)와 생성자 `triggerPolicy`, `edgeScore`, `recordProbe`(RTT EWMA, 연속 실패 DOWN, 지연 fence가 남은 Edge의 RECOVERING), `rankEdges`, `selectEligibleEdge`의 `maxLatencyMs`와 `exclude` 입력, `considerTrigger`의 `availability`와 `performance` 종류, 출발 CSE 무응답 failover(cached checkpoint, 지연 fence, 지연 구독 해제), `reconcileRecoveredEdge`, `checkpoint`, CUTOVER 추가 replay 최대 3회, RESTORE 단계 callback probe, 구독 해제 뒤 callback receipt 초기화, `onEvent` 측정 hook을 추가함. failover 모드는 coordinator가 출발 CSE probe 실패를 관측한 경우에만 켜짐.
- `pc-mobius/integration/src/handover-automation.mjs`: `HandoverAutomation`(zone 보고, probe, 성능 평가, 검토 상태 재개, 주기 checkpoint)과 `ObservationForwarder`(make-before-break 경로 선택, cutover 보관, 재전송 dedup, 실패 재시도, warm standby 복제)를 추가함.
- `pc-mobius/scripts/run-handover-auto-real.mjs`: 위 구성의 실제 CSE 실행과 receipt 생성을 담당함.

## 해석

- zone과 performance 이동은 make-before-break로 동작함. 대상 CSE 복원과 replay는 출발 CSE가 계속 기록하는 동안 끝나고, Gateway 보관 구간은 p50 55.3ms임.
- edge-a에서 edge-b로 가는 zone, load 이동은 보관 구간이 약 65ms에서 245ms임. edge-b의 RTT 18ms가 CUTOVER replay, VERIFY readback 왕복에 곱해짐.
- 지연 주입 이동은 느린 출발 CSE(편도 40ms)의 fence 왕복이 보관 구간(약 280ms에서 345ms)에 포함되고, 중단은 약 190ms에서 235ms임.
- availability 이동의 중단(약 720ms에서 790ms)은 감지(약 215ms에서 280ms)와 대상 CSE 등록, 복원(약 500ms에서 530ms)의 합임. 출발 CSE가 응답하지 않으므로 마지막 checkpoint(나이 약 495ms에서 715ms)로 switch 상태를 복원하고, 중앙 accepted 기록으로 관측을 replay함.
- warm standby 복제가 대기 CSE를 최신으로 유지하여 failover replay 양이 회당 5건에서 6건임. 재시작 뒤 failback은 종료 구간의 관측 약 80건을 출발 CSE가 계속 기록하는 동안 replay하므로 중단 p50이 약 56ms임.
- 중복 알림 699건은 대상 CSE replay와 standby 복제로 생긴 CIN 생성 알림임. 앱 dedup이 sequence 기준으로 모두 정리하고, CSE container는 CIN 이름 `obs-<sequence>` 유일성으로 sequence당 1건을 유지함.

## 한계

- 단일 물리 호스트와 loopback 환경임. RTT 차이는 proxy 주입값이고 실제 WAN 또는 무선 구간 측정은 다음 단계 과제임.
- 장치는 모의 telemetry이고, 위치는 스크립트 MEC Location 보고이며, load 값은 시나리오가 넣은 edge-agent 보고값임. BLE 키링과 Raspberry Pi Gateway 실물 경로는 별도 receipt 대상임.
- coordinator store는 실행 전용 in-memory 구현(transaction마다 collection 얕은 복사)임. 파일 store와 PostgreSQL store는 transaction마다 전체 상태를 복제하므로 20Hz 관측 수용에는 행 단위 store 개선이 필요함.
- 트리거 정책은 실행용 축약값(체류 1.5s, cooldown 1.5s, zone dwell 0.5s, performance dwell 0.6s)임. 운영 기본값(30s, 60s, 10s)으로 30회를 반복하려면 30분 이상의 실행이 필요함.
- GatewayBridge 최신 상태 PUT 137건은 보관 구간에 전송 대기 대신 다음 telemetry로 덮어쓰는 최신값 방식으로 처리됨. sequence 관측은 보관 뒤 전달함.
- failover 동안 출발 CSE fence와 구독 해제는 복구 정산 시점에 적용함. 그 사이 출발 CSE 프로세스는 종료 상태임.
- availability 중단 약 0.78s를 더 줄이려면 standby 사전 등록으로 failover 시 register와 restore 왕복을 줄이는 작업이 다음 후보임.
