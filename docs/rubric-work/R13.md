# R13 oneM2M-MEC 애플리케이션 배치와 MEC 호스트 간 재배치

oneM2M MEC IPE를 MEC 애플리케이션 이미지(`pb-onem2m-ipe`)로 만들어 ETSI MEC Sandbox(STF_685)의 MEP에 배치하고, 거주자가 집(Edge-A, `mep1`)에서 공원(Edge-B, `mep2`)으로 걸어갈 때 MEC021 AMS 알림을 받아 IPE 인스턴스를 `mep1`에서 `mep2`로 재배치함. 실제 sandbox `dayofcare` 실행에서 검사 25개 중 25개가 통과함.

DOC-REV 2.0.0. 참조 문서 번호는 oneM2M TR-0086(oneM2M과 MEC 연동)임. 자원 이름, content schema, 결정 규칙은 이 저장소에서 정의함.

## 이야기와 시간 압축

혼자 사는 70대 후반 거주자의 하루를 sandbox 시나리오 `day-of-care`로 옮김. 키링은 거주자가 지닌 휴대폰(UE `resident-relay`)과 BLE로 연결되므로 네트워크 위치는 이 UE의 위치임. 이야기의 분 단위 시간은 실행에서 초 단위로 압축함.

최종 실행 시각에 같은 sandbox에서 R17 실험이 시나리오 UE 세 개를 움직이고 있었음. 그래서 실행 스크립트가 SCENARIO-UPDATE `ADD`로 같은 POA, 무선 설정, 역할을 가진 사본 UE `r13-resident`(거주자 휴대폰), `r13-carer`(요양보호사), `r13-guardian`(딸)을 만들어 이야기를 진행하고, 끝에 `REMOVE`로 지움(`PB_UE_PREFIX=r13-`). 사본 목록과 이유는 receipt `scenario.ueCopies`에 있음. 시나리오 UE를 그대로 쓰는 실행은 `PB_UE_PREFIX` 없이 같은 명령으로 진행함.

| UE | 역할 | 경로와 속도 |
|---|---|---|
| `resident-relay` | 거주자 휴대폰(키링 BLE 중계), 거주자 네트워크 위치 | 집, Boulevard de Belgique, 공원 동문, 보행로, 갈림길, 벤치, 0.9 m/s |
| `caregiver` | 방문 요양보호사 | 거리에서 현관까지, 1.3 m/s |
| `guardian` | 사무실에서 일하는 딸 | 사무실에서 벤치까지, 4 m/s |

각 MEP는 MEC011, MEC012, MEC013, MEC021만 실행함(공유 VM 부하 관리). MEC021 설정은 `MEEP_MEP_COVERAGE=mep1:home-district/mep2:park-district:office-district`임. MEC013과 MEC012는 자기 locality 안의 UE만 보므로, 거주자가 공원 구역에 들어가면 `mep1`의 MEC013 조회 결과에서 거주자가 빠지고 `mep2`의 결과에 나타남. 이 성질 때문에 거주자를 계속 따라가려면 IPE가 `mep2`로 옮겨 가야 함.

## 호스트 구성

| 호스트 | 역할 | 주소 |
|---|---|---|
| PC(Windows 11) | Mobius4 4.24.5 CSE `/pb-cse`(LAN HTTPS 17599, 실습 CA 서버 인증서, PC AE용 loopback HTTP), PostgreSQL과 PostGIS, orchestrator AE `Cpb-orchestrator`, 보호자 앱 AE `Cguardian-app`, 이야기 구동 스크립트 | <PC_IP> |
| VM `mec-sandbox`(Ubuntu 22.04, 단일 노드 kubeadm) | ETSI MEC Sandbox STF_685, sandbox `dayofcare`, MEP 2개, IPE pod | <VM_IP> |

IPE pod는 ingress `https://<VM_IP>/dayofcare/<mep>`로 MEC API를 쓰고(고정 CA), PC CSE에는 HTTPS로 연결함. CSE는 pod의 NodePort(`http://<VM_IP>:31881`, `31882`)로 oneM2M 알림을 보내고, MEC 서비스도 같은 NodePort로 콜백함.

## 호스트 적격성

규칙은 `pc-mobius/integration/src/mec-ipe-orchestrator.mjs`의 `evaluateEligibility`에 있음.

- 적격 조건: 호스트의 MEC013과 MEC012 locality가 대상 구역을 포함함, MEC011, MEC012, MEC013, MEC021이 시나리오에 선언됨, 그 MEP의 MEC011 목록이 200으로 응답하고 MEC012와 MEC013이 ACTIVE임, 선언 용량에서 이미 배치한 사용자 앱 요청을 뺀 여유가 IPE 요청(CPU 0.1, 메모리 64 MiB) 이상임.
- 순서: MEC021 coverage가 대상 구역에 대응시키는 호스트를 먼저, 그다음 여유 CPU가 큰 호스트를 고름.

실행의 결정 기록은 다음과 같음(receipt `decisions`).

| 결정 | 계기 | 대상 구역 | mep1 판정 | mep2 판정 | 선택 | 평가 시간 |
|---|---|---|---|---|---|---|
| 초기 배치 | MEC013 위치 조회 | home-district | 적격 | 부적격(locality ["park-district","office-district"] excludes home-district) | mep1 | 41 ms |
| 사전 배치 | oneM2M 관측 알림과 MEC013 접속 POA(moneghetti-4g-macro) | park-district | 부적격(locality ["home-district"] excludes park-district) | 적격 | mep2 | 164 ms |
| 재배치 | MEC021 INTERHOST_MOVEOUT_TRIGGERED | park-district | 부적격(locality ["home-district"] excludes park-district) | 적격 | mep2 | 122 ms |

## 오케스트레이션 단계

1. 선언 배치: 시나리오가 `pb-ipe-mep1`을 `mep1`의 EDGE-APP 프로세스로 선언함(고정 app instance ID, NodePort 31881, `meSvcName: pb-onem2m-ipe`, CPU 0.1~0.5, 메모리 64~256 MiB). sandbox virt-engine이 pod를 만들고 app store가 `mep1`의 app instance로 등록함.
2. IPE 시작: pod가 CSE 응답을 기다린 뒤 AE `pb-mec-ipe`를 등록하고, MEC011 `confirm_ready`(204), 자기 서비스 등록(201), AppTermination 구독(201), MEC021 등록과 MobilityProcedure 구독을 마친 뒤 `lifecycle` 컨테이너에 READY cin을 씀.
3. 초기 배치 결정: orchestrator가 MEC013으로 거주자 구역(home-district)을 확인하고 적격성 기록을 남긴 뒤 `ownership` 컨테이너에 epoch 1(소유자 `mep1` 인스턴스) cin을 씀.
4. 요청: 보호자 앱이 Location periodic, Location user event, RNIS cell change 요청 cin을 씀. `mep1` 인스턴스가 `mep1`의 MEC013/MEC012 구독을 만들고 장치 AE `resident-keyring`의 `location` 컨테이너에 관측 cin을 씀.
5. 요양보호사 방문: `mep1`의 MEC013이 요양보호사와 거주자를 같은 `home-wifi` AP에서 보여 줌.
6. 사전 배치: Edge-A에서 온 관측 cin 알림마다 orchestrator가 MEC013으로 접속 POA를 확인함. `moneghetti-4g-macro`는 반경이 공원 구역 POA와 겹치는 경계 셀이므로 park-district 적격성을 평가하고 SCENARIO-UPDATE `ADD`로 `pb-ipe-mep2`(NodePort 31882)를 `mep2`에 배치함. 새 인스턴스는 대기 상태로 READY를 쓰고 MEC021에 같은 UE를 등록함.
7. 재배치 계기: 거주자가 park-district에 들어가면 MEC021이 `mep1` 인스턴스에 `INTERHOST_MOVEOUT_TRIGGERED`(대상 app instance = `mep2` 인스턴스)를 보냄. `mep1` 인스턴스가 이를 lifecycle cin으로 남기고, orchestrator가 적격성을 다시 평가해 epoch 2(소유자 `mep2` 인스턴스) cin을 씀.
8. 인계: `mep1` 인스턴스가 MEC 구독 3건을 삭제하고(HANDED_OVER) MEC021에 context transfer 완료를 알림. `mep2` 인스턴스가 CSE의 요청 컨테이너에서 활성 요청을 다시 읽어 `mep2`의 MEC013/MEC012 구독을 만들고, 같은 `location` 컨테이너에 관측을 이어 씀. 모든 상태와 관측 cin에 `servedBy {mep, appInstanceId, epoch}`가 들어감. 소유자가 아닌 인스턴스는 요청 cin을 미루고 늦은 MEC 콜백을 FENCED로 막음.
9. 정상 종료: 갈림길 정지 시점에 orchestrator가 SCENARIO-UPDATE `REMOVE`(gracePeriod 30 s)로 `pb-ipe-mep1`을 제거함. app store가 MEC011 AppTermination을 보내고, IPE가 서비스 등록과 MEC021 등록을 정리한 뒤 `confirm_termination`(204)을 보내면 sandbox가 노드와 pod를 지움.
10. 마무리: 보호자 앱 해지 cin으로 `mep2` 구독을 지우고, `pb-ipe-mep2`를 같은 방식으로 제거한 뒤 선언 배치(`pb-ipe-mep1`)를 복원함.

## 재현 명령

```bash
# 시나리오 반영과 sandbox 생성(VM 내부 platform-ctrl 경로)
scp deploy/mec-sandbox/scenarios/day-of-care.yaml mec@<VM_IP>:~/day-of-care.yaml
ssh mec@<VM_IP> 'bash -s' < deploy/mec-sandbox/import-day-of-care.sh
# IPE 이미지 빌드와 push(.local/mec-sandbox/ca.pem 필요)
bash deploy/mec-sandbox/ipe/publish-image.sh
# 이야기 실행(.local/mec-sandbox/pc-cse-server.key/.crt, .local/postgres/connection.json 필요)
MOBIUS4_ROOT=<mobius4 경로> npm --prefix pc-mobius run integration:mec-day-of-care
# 다른 실험이 시나리오 UE를 쓰는 동안에는 사본 UE로 실행
MOBIUS4_ROOT=<mobius4 경로> PB_UE_PREFIX=r13- npm --prefix pc-mobius run integration:mec-day-of-care
```

최종 receipt는 `status: PASS`, 검사 25개, trace 242줄(SHA-256 `deb9efc039de3b773ba0289dcdea58619d90adda190978ce6d5496adb52ca995`)이며, IPE 이미지는 `meep-docker-registry:30001/pb-onem2m-ipe@sha256:a5c8262b65a37299b3aa6e618a661cb6d1211add1d60d5b42181d502b8dd0582`임. app instance ID는 mep1 `0d0c0a00-0000-4000-8000-0000000001a1`, mep2 `0d0c0a00-0000-4000-8000-0000000001a2`임.

## sandbox에서 확인한 동작

| 관찰 | 반영 |
|---|---|
| virt-engine이 프로세스 `environment`를 `,`와 `=`로 나눔 | 환경 값은 두 문자를 뺀 형식으로 쓰고, 목록은 `;`로도 나눔 |
| `meSvcName`이 같은 프로세스는 같은 app 이름을 가짐 | MEC021이 두 인스턴스를 인접 app instance로 다루고 대상 ID를 알림에 넣음 |
| app instance ID가 같은 컨테이너가 다시 시작하면 MEC021 등록과 MEC011 서비스가 남아 알림이 중복됨 | 시작할 때 같은 ID의 이전 등록과 서비스를 지움 |
| `Onem2mHttpClient`는 원격 CSE에 HTTPS를 요구함 | PC CSE를 실습 CA 서버 인증서로 LAN HTTPS에 열고 pod는 고정 CA로 접속함 |
| `kubectl logs -f`가 inotify 한도로 실패함 | run script가 SSH로 `kubectl logs`를 주기적으로 읽어 trace에 넣음 |
| GIS는 같은 기술의 현재 POA가 범위 안이면 그 POA를 유지함 | 갈림길 정지는 POA 이름 대신 MEC013 좌표(15 m 이내)로 확인하고 실제 POA를 기록함 |
| 5G에서 4G로 옮길 때 MEC012 cell change 알림이 0건임(receipt `rnisCellChanges` 빈 목록) | 사전 배치 계기를 oneM2M 관측 알림과 MEC013 접속 POA 조회로 둠 |
| periodic 구독(reportingInterval 2 s)의 실제 알림 간격은 약 4 s임 | 손실 보고 수는 측정 주기로 계산함 |
| 같은 sandbox를 다른 실험(R17)이 함께 씀 | 실행 전 6 s 동안 이 실행이 움직일 UE의 위치가 바뀌면 `SANDBOX_IN_USE`로 실행을 멈춤. 사본 UE 옵션 `PB_UE_PREFIX`를 둠 |
| 실행 중 추가한 UE에 GIS 위치를 처음 보낼 때 400(`duplicate key "ue_pkey"`)이 오고, 이름이 `r13-resident-relay`면 다시 만들어도 400(`varchar(36)`)이 옴 | geodata를 지운 뒤 다시 보내고, 사본 이름을 12자 이하(`r13-resident`)로 둠 |
| MEC011 AppTermination 뒤 MEC021 등록과 구독 DELETE가 404임 | sandbox가 app 제거 때 MEC021 등록을 먼저 지운 상태이며, 종료 확인(`confirm_termination` 204)은 정상임 |

## 한계와 다음 단계

- MEC 쪽은 실제 sandbox이고 UE는 sandbox 시나리오 UE와 그 사본임. 실물 키링, 실제 이동통신망 위치, 실제 MEC 호스트 하드웨어로 넓히는 실행은 다음 단계임.
- MEP 두 개는 같은 단일 노드 k8s 위의 논리 호스트임. 호스트 용량은 시나리오 `meta`의 선언값이며 pod 자원 요청과 함께 적격성 계산에 들어감.
- IPE 인스턴스마다 정밀 좌표 암호화 키가 다름. 인스턴스 간 키 공유는 k8s Secret 연동이 필요하며, 지금은 관측 cin의 격자 좌표(`loc`, 소수 셋째 자리)가 인스턴스와 무관하게 이어짐.
- 사전 배치 규칙은 경계 셀 한 단계 예측임. 여러 후보 구역이 있는 경우에는 이동 방향과 평소 산책 시각(R17의 정상 패턴)을 함께 쓰는 규칙이 필요함.
- oneM2M handover(Edge-A CSE에서 Edge-B CSE로, epoch 증가)는 R15와 R16 실행이 다루며, 이 실행의 CSE는 PC의 Mobius4 하나임. 두 흐름을 한 실행에서 묶는 작업이 다음 단계임.
