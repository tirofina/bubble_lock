# R15 지리 위치, R16 MEC 서비스 작업 기록

MEC IPE가 MEC011 서비스 목록을 oneM2M flexContainer로 게시하고, oneM2M 요청 cin을 MEC013/MEC012 구독으로 바꾸고, MEC 알림을 장치 AE의 location/rnis cin으로 기록함. 정책, geofence, handover 판단은 oneM2M 구독 알림만 사용함. 실제 Mobius4 4.24.5 두 개와 로컬 MEC 샌드박스 시뮬레이터 실행에서 검사 29개 모두 통과함.

## 흐름

1. IPE가 MEC011 `mec_service_mgmt/v1/services`를 조회하고 Location(MEC013), RNIS(MEC012), WAIS(MEC028), App Support(MEC011)를 `mec:mecSvc` flexContainer 4개와 group 1개로 게시함. 앱은 `fu=1&ty=28` discovery로 MEC 서비스를 oneM2M 안에서 찾음.
2. 보호자 앱 AE가 `locationRequests`/`rnisRequests`에 요청 cin을 씀. 내용은 `op`, `requestId`, `deviceAe`, `ueAddress`, `type`, `durationSec`, `intent`(policyId, grantId, grantRevision, policyRevision)임.
3. IPE는 cin 생성자(`cr`) 허용 목록, 현재 grant revision, 승인 정책의 장치 결속을 확인한 뒤 MEC013 `subscriptions/users`(v3) 또는 `userTracking`/`periodic`/`zonalTraffic`(v2), MEC012 `CellChangeSubscription`을 생성함. 결과는 `requestStatus` cin으로 앱에 알림.
4. MEC 알림이 IPE callback으로 들어오면 UE 주소와 구독 링크 결속, 중복, 30초 지연, 2초 미래, 순서 역전을 검사하고 `<device-AE>/location` 또는 `<device-AE>/rnis`에 cin을 기록함. location cin은 `loc`(GeoJSON Point, 소수 셋째 자리 격자)와 AES-256-GCM 정밀 좌표 암호문을 담음. rnis cin은 셀 중심점 `loc`을 담음.
5. 정책 AE는 두 컨테이너를 구독하고, rnis 셀이 승인 정책의 `servingCells` 안에 있을 때만 위치 관측을 HEALTHY로 판정함. 위치가 geofence 안에서 10초 연속 체류하고 소유 CSE 체류가 30초를 넘으면 `HandoverCoordinator`가 edge-a에서 edge-b로 전환함.
6. 앱은 `?fu=1&ty=3&gmty=3&gsf=1&geom=<polygon>` geo-query로 zone 안의 장치를 찾음.
7. `op: unsubscribe` cin, 요청 cin 삭제(net 4), 장치 AE 삭제(net 2), grant 회수가 각각 MEC 구독 삭제로 이어짐. 만료 전 PUT 갱신과 공급자 구독 소실 시 재생성도 수행함.

## 루브릭 대응

- R16 Expert: MEC011 discovery 결과를 oneM2M 자원으로 게시하고(발견), 요청 cin으로 MEC013/MEC012 구독을 생성, 갱신, 삭제하며(구성), 알림과 MEC013 사용자 조회, MEC011 `confirm_ready`를 사용함(소비). oneM2M에서 MEC로, MEC에서 oneM2M으로 양방향 흐름이 trace에 남음.
- R16 기존 Emerging 경로: PC가 MEC API를 직접 호출하는 `MecSubscriptionManager`는 `core.mec.path=direct`로 유지함.
- R15 Expert: 네트워크 위치(RNIS 셀), MEC 위치(MEC013 좌표), oneM2M 위치(`loc`, geo-query)를 결합해 geofence, 정책, handover 판단에 사용함. 모든 판단은 oneM2M 알림으로 시작하는 이벤트 방식임.

## 확인한 Mobius4 동작

- 구독 생성에는 부모 자원의 CREATE와 RETRIEVE가 함께 필요함(acop 3). Mobius4 4.24.5의 ACP 판정은 acop 비트만 사용하므로 소비자는 cin `cr`이 IPE AE-ID인지 확인함. 실행에서 앱이 쓴 위조 관측은 `creator-review`로 걸러짐.
- AE가 자기 AE의 빈 acpi를 처음 채우는 UPDATE는 5000을 반환함. 장치 AE의 ACP 연결은 handover-cse.mjs와 같은 방식으로 CSE admin이 수행함.
- `<group>`은 `<container>` 아래에서 4108을 반환하므로 IPE AE 아래에 둠.
- `<node>`, `<locationPolicy>`, announcement 대신 container, flexContainer, `loc` 속성을 사용함.

## 실제 sandbox 실행 (2026-11-20)

실제 ETSI MEC Sandbox(STF_685)에 IPE를 연결해 33개 확인 항목이 모두 PASS함. MEC 쪽은 시뮬레이터가 아닌 sandbox이며, receipt의 `simulation`은 `{ mec: false, ue: 'sandbox-scenario', cse: false }`임.

| 항목 | 값 |
| --- | --- |
| MEC 쪽 | VirtualBox VM 192.168.0.103의 STF_685 로컬 설치(kubeadm), sandbox `bubble`, 시나리오 `dep-opt-b`(배치 옵션 B, MEP 4개), MEP `mep1` |
| oneM2M 쪽 | PC의 Mobius4 4.24.5 두 개(edge-a, edge-b), PostgreSQL 17.6과 PostGIS 3.7 |
| 전송 | MEC API는 HTTPS, ingress 인증서는 로컬 CA(`IP:192.168.0.103` SAN)로 고정 검증함. CA 없는 접속은 `MEC_TRANSPORT_REVIEW`로 거부됨. MEC 알림은 sandbox pod에서 PC LAN 주소로 들어옴 |
| UE 이동 | sandbox GIS 엔진의 위치 갱신과 MOBILITY 자동화를 사용함. POA 변경과 RNIS cell change는 sandbox가 직접 만듦 |
| 실행 명령 | `npm --prefix pc-mobius run integration:mec-ipe-sandbox` |
| receipt | `docs/verification-evidence/2026-11-20/mec-ipe-sandbox.json`, trace `mec-ipe-sandbox-trace.jsonl`, 알림 원문 `mec-sandbox-raw/notifications.json` |

결과는 다음과 같음.

- MEC011: IPE 앱 인스턴스를 sandbox에 등록하고 `confirm_ready`가 204로 끝남. IPE는 자기 서비스(`pb-onem2m-ipe`)를 MEC011에 등록했고, 같은 MEP의 서비스 목록에서 조회됨. 종료 때 서비스와 앱 인스턴스를 삭제함.
- 발견: sandbox 목록의 MEC021, MEC033, MEC012, MEC013, MEC046, MEC040, 공식 meep-ipe 서비스가 모두 `mec:mecSvc` flexContainer로 게시되고, 앱은 oneM2M 발견(`fu=1&ty=28`)으로만 읽음.
- 양방향 흐름: 요청 cin 3건(Location periodic, Location user event, RNIS cell change)이 sandbox 구독 3건(id 5, 6, 6)이 됨. 실제 알림 19건(periodic 13, user event 4, cell change 2)이 장치 AE의 location, rnis cin으로 기록되고, 앱 구독 알림과 정책 판정으로 이어짐.
- 지오펜스와 handover: zone2(학교) POA 영역으로 이동한 뒤 29.2초 만에 zone 트리거가 ACTIVE가 되어 edge-a에서 edge-b로 전환됨(epoch 2). RNIS 판정은 이동 때 `network-corroborates-target`, 귀가 때 `network-cell-outside-target`임. zone2 진입 이벤트는 좌표가 없어 MEC013 user query로 좌표를 채움.
- geo-query: 학교 영역에서 장치 1건, 집 영역에서 0건이 나옴.
- 갱신과 해지: Location과 RNIS 구독이 각각 2회 PUT으로 갱신됨. RNIS 해지 cin과 장치 AE 삭제로 sandbox 구독 3건이 모두 204로 삭제되고, 해지 뒤 늦은 RNIS 알림은 `TOMBSTONE`으로 처리됨.
- 콜백 위생: sandbox 실제 알림을 다시 보내 중복, 오래된 시각, 미래 시각, 다른 UE를 각각 `DUPLICATE`, `STALE`, `FUTURE`, `BINDING_REVIEW`(403)로 걸러냄.

## sandbox에서 확인한 동작과 반영한 수정

| 관찰 | 반영 |
| --- | --- |
| MEC012 `associateId.type`과 `hoStatus`를 문자열로 보내면 sandbox가 500(int32 해석 실패)을 반환함 | 클라이언트가 정수 열거값(1, 3)을 보냄. 시뮬레이터도 정수 형식을 사용함 |
| `filterCriteriaAssocHo.appInstanceId`가 UE 쪽 앱과 대조되어, IPE 자신의 앱 ID를 넣으면 cell change가 오지 않음 | RNIS 필터에서 IPE 앱 ID를 제외함 |
| Location v3와 RNIS의 PUT은 본문 `_links.self.href`가 구독 ID와 같아야 함(400) | 갱신 PUT에 self 링크를 넣음. 시뮬레이터도 같은 규칙을 적용함 |
| RNIS 구독 목록이 `_links.subscription` 아래에 있음(MEC012 SubscriptionLinkList) | 목록 해석에 이 형식을 추가함 |
| 재시작한 MEC 서비스가 이전 등록을 지우지 않아 MEC011 목록에 같은 서비스가 여러 번 나옴 | 인스턴스마다 별도 flexContainer 이름(`RNIS-<id 앞 8자>`)을 사용함 |
| loc-serv가 구독 잠금을 잡은 채 알림을 보내므로, 같은 구독의 DELETE가 알림 응답을 기다림 | IPE가 알림을 요청별 별도 큐에서 처리하고, 알림이 부른 갱신과 해지는 응답 뒤 백그라운드로 실행함. 해지 중 들어온 알림은 즉시 `TOMBSTONE`으로 응답함 |
| MOBILITY 자동화는 시작 직후 첫 주기에 기준 POA를 잡음 | 실행 시작 때 자동화를 켜고 4초 기다린 뒤 이동함. 종료 때는 집으로 옮긴 뒤 자동화를 원래 상태로 돌림 |

sandbox 원 저장소(STF_685 backend `8c66f08`)의 결함 두 건은 VM의 로컬 설치에서 고쳐 사용함. 변경분은 `docs/verification-evidence/2026-11-20/mec-sandbox-patches/`에 있음.

- `meep-rnis`: 구독이 처음 expiryDeadline에 닿으면 `checkForExpiredSubscriptions`에서 nil 포인터(`link.Subscription`)로 pod가 재시작되고 RNIS 상태가 모두 사라짐. PUT 갱신이 예전 만료 항목을 남겨 갱신된 구독도 예전 시각에 삭제됨. 포인터 초기화와 현재 expiryDeadline 비교를 넣음.
- `meep-loc-serv`: user event 알림의 `_links.subscription.href`를 모든 구독을 도는 반복에서 고르므로 다른 구독 ID가 들어감. 일치한 구독(`subsId`)의 링크를 사용하도록 고침.

두 건은 ETSI MEC Sandbox 저장소(labs.etsi.org/rep/mec/etsi-mec-sandbox)에 공개 issue로 올릴 후보임.

## 서버 CSE 연결 실행 (2026-11-20)

sandbox `dayofcare`의 IPE pod `pb-ipe-mep1`을 팀 서버 CSE(Mobius4 `/bubble-cse`, 같은 VM의 Docker)에 연결함. receipt는 `docs/verification-evidence/2026-11-20/mec-ipe-server-cse.json`, trace는 `mec-ipe-server-cse-trace.jsonl`이며 상태는 PARTIAL임. 마무리 요청으로 보행 도중 실행을 멈춤.

| 항목 | 값 |
| --- | --- |
| 전송 | nginx 발신자 결속 경로 `https://<SERVER_DOMAIN>:8443/onem2m/Mobius`, 상호 TLS(클라이언트 인증서 CN `pb-mec-ipe`), pod hostAlias로 SNI와 Host를 `<SERVER_DOMAIN>`로 맞춤 |
| 준비 | `provision-server-cse.sh`가 cse 컨테이너 안에서 `bubble-household-1/resident-relay`와 `location`, `rnis` 컨테이너, ACP `resident-relay-mec-access`를 만듦. 권한은 `Cpb-mec-ipe` 7, `Cpb-dash-guardian` 50, `Cpb-dash-operator` 34임. 가구 AE의 acpi는 그대로임 |
| pod 연결 | `attach-server-cse.sh`가 VM에서 secret `pb-ipe-server-cse`를 만들고 `pb-ipe-mep*` 배포에 볼륨, hostAlias, `ONEM2M_*` 환경 변수를 넣음. 이미지에는 공개 lab CA만 들어 있음 |
| 결과 | IPE AE `/Mobius/pb-mec-ipe` 등록 2001, 요청 cin 2건(`v0cak4eyf8`, `0xb1etmda8`)이 mep1의 MEC013, MEC012 구독(201)이 됨. Location 알림 9건이 `/Mobius/bubble-household-1/resident-relay/location` cin으로 기록됨(첫 cin `rijtgz1eax`). `Cpb-dash-guardian` 구독이 PC 수신기에 알림을 전달함. 구독마다 PUT 갱신 1회(200) |
| 복원 | `resident-relay`를 집 위치로 되돌리고 MOBILITY 자동화를 실행 전 상태(꺼짐)로 돌림. IPE pod와 MEC 구독 2건은 계속 동작함 |

- 서버 CSE는 `NOTIFICATION_ALLOWED_ORIGINS`에 등록한 주소로만 알림을 보냄. 목록이 비어 있던 동안 모든 구독이 4000 `notification target origin denied`를 받았고, 서버 담당이 IPE NodePort와 PC 수신기 주소를 등록한 뒤 IPE가 시작함.
- 장치 삭제 감시 구독은 nginx가 `bubble-household-1/<x>/(location|rnis)` 밖의 경로를 막으므로 403이며 IPE는 `DEVICE_WATCH_REVIEW`로 기록함. 관측 기록은 영향을 받지 않음.
- `pb-ipe-mep*` 배포는 virt-engine의 Helm release임. 시나리오 재활성화나 `SCENARIO-UPDATE ADD`는 시나리오 yaml로 다시 만들기 때문에 그 뒤에 attach 스크립트를 다시 실행함. 시나리오 yaml은 R13 실행기가 쓰는 PC CSE 기본값을 유지함.
- 남은 일: RNIS cell change 알림, 갱신 2회 이상, 해지 204 확인은 다음 실행에서 확인함. 요청자 경로로 쓴 LAN relay가 내려가므로 다음 실행에는 요청자용 인증서 경로나 docker exec 경로가 필요함.

## 한계와 다음 단계

- MEC 쪽은 실제 sandbox이며 UE는 sandbox 시나리오의 UE임. 실물 키링과 실제 이동통신망 위치는 사용하지 않음.
- sandbox는 PC와 같은 LAN의 VM 1대에 직접 설치한 ETSI MEC Sandbox(STF_685)임. 설치 절차와 로컬 수정 내역은 `deploy/mec-sandbox/README.md`에 있음.
- RNIS와 loc-serv 수정은 로컬 설치에만 반영되어 있음. 원 저장소 sandbox에서는 RNIS 구독이 첫 만료 시각에 서비스를 재시작시키므로 expiryDeadline 없이 쓰거나 위 수정이 필요함.
- handover 뒤에도 장치 location 컨테이너는 IPE가 있는 edge-a CSE에 남음. 대상 CSE로 관측 경로를 옮기는 작업은 별도 설계가 필요함.
- 정책 AE와 앱이 구독을 위해 CREATE 권한을 함께 가지므로, 관측 신뢰는 `cr` 확인과 IPE 전용 키 암호문에 의존함.
- 웹 대시보드가 oneM2M location/rnis 컨테이너와 requestStatus를 직접 표시하는 화면은 WEB-DASHBOARD 담당 작업으로 남음.
