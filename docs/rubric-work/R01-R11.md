# R01, R11 작업 기록 (DOC-REV 2.0.0)

보호자가 승인한 가구 전체 명령이 oneM2M `<grp>/fopt` 요청 한 번으로 실행되고, 실제 Mobius4 4.24.5에서 구성원별 rsc, 실패 구성원만 재시도, 구성원별 ACK와 readback이 확인됨. TS-0023 `cod:binSh`는 JavaScript 클라이언트와 표준 라이브러리 Python 독립 클라이언트가 같은 discovery와 state 결과로 사용함.

## 구현 구성

| 파일 | 역할 |
|---|---|
| `pc-mobius/src/onem2m-group-fanout.mjs` | `<grp>` 생성과 갱신(mt=28, mid, macp, et), `<grp>/fopt` UPDATE, `m2m:agr/m2m:rsp` 구성원별 rsc 해석, 구성원 UPDATE와 RETRIEVE, cin 기록 |
| `pc-mobius/src/group-dispatcher.mjs` | `bridge.fanOut` 모드, `retryScope: failed`, commandId 단위 멱등 dispatch, 구성원별 claim binding과 readback 보존 |
| `pc-mobius/integration/src/group-command-service.mjs` | 가구 Group 명령 서비스. CSE가 수락한 구성원에게만 GatewayControl canonical claim 발급, Gateway receipt 뒤 CSE readback과 ACK cin 기록 |
| `pc-mobius/integration/src/portal-service.mjs` | `commands/request`의 `target: household`, `commands/approve`의 Group 경로, `commands/retry` 경로, snapshot의 실시간 `group` 보기 |
| `pc-mobius/integration/src/gateway-control.mjs` | `onReceipt` 수신기. 정산된 device receipt를 Group 서비스에 전달함 |
| `pc-mobius/scripts/run-group-command-real.mjs` | 실제 Mobius4 실행과 receipt 작성 |
| `tools/onem2m-sdt-client/sdt_client.py` | 공개 XSD와 TS-0023 cnd만 사용하는 Python 독립 클라이언트 |

단일 기기 명령은 기존 `gatewayControl.issue` 경로 그대로임. Group 경로는 요청의 `target: household`에서만 동작함.

## R01 실행 흐름

1. 방문자가 `target: household`로 요청하고 서버가 가구 등록 기기 2~16대를 구성원으로 정함.
2. 보호자 승인 시 서비스가 `<grp>`를 확인함. mid는 각 키링 AE의 `cod:binSh` flexContainer, macp는 중앙 명령 AE 전용 ACP, et는 보호자 grant 만료 시각임.
3. `PUT <grp>/fopt {"cod:binSh":{"state":true}}` 한 번을 보내고 `m2m:agr` 응답에서 구성원별 rsc를 읽음.
4. rsc 2004 구성원마다 claimId, grantRevision, ownershipEpoch, deadline, payloadHash를 가진 canonical command를 발급함. 실패 구성원은 `RETRY_PENDING`과 `CSE_MEMBER_RSC_<rsc>`로 기록함.
5. Gateway poll, authorize, dispatch-start, receipt가 구성원별 claim을 그대로 사용함. receipt 정산 뒤 서비스가 구성원 flexContainer를 다시 읽고 `commandAcks` container(mni=1)에 et가 있는 ACK cin을 남김.
6. `commands/retry`는 `RETRY_PENDING` 구성원에게만 구성원 UPDATE를 보내고 같은 memberCommandId로 claim을 발급함. 상태는 IntegrationStore(JSON 또는 PostgreSQL)에 남고 재시작 뒤에도 이어짐.

## R11 SDT 상호운용

- Python 클라이언트는 XSD의 `targetNamespace` 접두사와 `sg_flexContainerResource` 요소에서 `cod:binSh`, `state`, `xs:boolean`을 읽음.
- 두 클라이언트가 `GET /Mobius?fu=1&ty=28&cnd=org.onem2m.common.moduleclass.binarySwitch`로 같은 3개 URI를 찾고 같은 state를 읽음.
- JavaScript 쓰기를 Python이 읽고, Python 쓰기를 JavaScript가 읽음. 미등록 cnd discovery 결과는 빈 목록임.
- 키링 bench는 배포 단위 profile 선택 방식임. Mobius4 registry가 cnd 하나에 envelope 하나를 연결하기 때문임. 새 scoped 배포는 `r4-common-1.0`, 기존 bench volume은 `pb-legacy-1.0`(deprecated)으로 동작함. bootstrap은 기존 자원의 envelope를 인정하고, Feather relay readback은 두 envelope를 모두 읽음.

## 한계

- 장치 응답이 늦은 구성원은 deadline까지 `DISPATCHED` 상태로 ACK를 기다림. 5초 claim 예약이 지난 구성원의 재시도에는 새 memberCommandId 발급 설계가 필요함.
- Mobius4 4.24.5는 macp를 fopt 진입 판정에 사용하고, 구성원별 결과는 각 구성원 acpi로 결정함. receipt의 4103 결과가 이 동작을 보여 줌.
- 이번 실행은 host 1대와 CSE 1개 구성임. 원격 CSE 구성원을 포함한 fan-out은 다음 실험 항목임.
- 실물 Raspberry Pi, BLE, 키링 하드웨어 경로의 Group 명령 실행은 bench 담당 receipt로 연결할 항목임.
- 대시보드 화면의 Group 표시는 WEB-DASHBOARD 작업 항목이며, snapshot은 `commandRequests[].group`으로 구성원별 상태를 제공함.
