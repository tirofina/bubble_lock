# R10 보안과 개인정보 보호 작업 기록

결론: 실제 Mobius4 4.24.5 두 대 앞에 TLS 1.3 상호 인증(mTLS) 프런트를 두고 인증서 하나를 AE originator 하나에 묶었으며, 기존 ACP 역할 행렬 828건을 포함한 918건이 모두 PASS임. 보안 프로토콜(TLS 1.3 mTLS)과 접근 제어 정책(ACP, Access Control Policy)이 같은 요청 경로에서 함께 동작함.

## 동작 방식

- 프런트는 TLS 1.3만 허용하고 실행별 로컬 CA가 발급한 클라이언트 인증서를 요구함. 만료, 다른 CA, serverAuth 전용 EKU 인증서는 HTTP 처리 전에 연결이 끊기고, 서버 감사 기록에 X.509 검증 코드가 남음.
- 인증서 식별자(SAN URI 우선, CN 보조)는 바인딩 표에서 정확히 하나의 originator에 대응함. 행마다 인증서 SHA-256 지문을 고정할 수 있어 같은 SAN을 가진 다른 키 인증서는 `ORIGINATOR_BINDING_CERTIFICATE_MISMATCH`로 거부됨.
- `X-M2M-Origin`이 비어 있으면 프런트가 바인딩된 값을 넣고, 같으면 그대로 전달함. 다른 값, `C`/`S` 자동 할당 요청, 중복 헤더는 HTTP 403, `X-M2M-RSC: 4103`, `pb:originatorBinding.code` 구조화 오류로 프런트에서 응답을 끝내므로 요청은 CSE에 도달하지 않음.
- `X-SSL-Client-*`, `X-Forwarded-*`, `Forwarded`, `X-Client-*` 같은 위조 가능한 신원 헤더는 제거함. CSE가 보는 신원은 프런트가 정한 originator 하나임.
- 바인딩 표는 요청마다 파일 상태(크기, 시각, inode)를 확인해 바뀌면 다시 읽음. 행을 지우면 같은 keep-alive TLS 소켓의 다음 요청부터 거부되며 프런트는 같은 프로세스로 계속 동작함. 표 형식이 깨지거나 파일이 없으면 전체 거부(fail closed, 503/5000)로 처리함.
- 감사 기록은 요청과 핸드셰이크 실패마다 JSONL 한 줄이며 `prevHash`와 `entryHash`로 이어짐. originator는 도메인 분리 SHA-256 digest 16자리로, 요청 본문은 SHA-256과 크기로만 기록함.
- MQTT: Mobius4 MQTT 바인딩은 payload의 `fr`로 권한을 판정하고 topic의 originator는 응답 주소로만 사용함(Mobius4 `bindings/mqtt.js` 주석에 명시됨). 그래서 두 단계로 묶음.
  1. Mosquitto가 TLS 1.3, `require_certificate`, `use_identity_as_username`으로 인증서 CN을 사용자 이름으로 쓰고, 바인딩 표에서 생성한 ACL로 자기 originator의 요청 topic 쓰기와 응답 topic 읽기만 허용함. 외부 listener에는 `mount_point ext/`를 두어 클라이언트 topic이 CSE topic 공간에 직접 닿지 않게 함. Mosquitto 2.0.22는 mount point가 붙은 topic으로 ACL을 검사하므로 생성 ACL도 `ext/` 접두어를 사용함.
  2. originator guard가 내부 listener에서 `ext/` 요청을 받아 `fr`이 topic originator와 같고 현재 표에 바인딩이 있을 때만 CSE topic으로 넘김. 나머지는 rsc 4103 응답 primitive로 돌려줌. guard도 같은 표 파일을 읽으므로 HTTP와 MQTT 회수가 한 번의 표 수정으로 함께 반영됨.

## 해석

기존 828건 행렬은 인증 없는 HTTP loopback에서 `X-M2M-Origin`을 그대로 받아들이는 구성이었음. 이번 실행에서는 같은 행렬이 인증서로 확인된 originator 위에서 같은 결과를 내고, 인증서와 다른 originator 주장은 CSE 도달 전에 차단됨. ACP는 originator별 권한을 정하고, 프런트와 guard는 그 originator가 실제 인증서 소유자임을 보장함. 회수는 표의 행 하나를 지우는 작업으로 HTTP와 MQTT에 함께 즉시 반영됨.

## 개인정보 보호

- 위치 임대(location lease): `pc-mobius/integration/src/location-privacy.mjs`의 `LocationPrivacyService`가 보호자 승인으로 1~300초 임대를 만들고, 조회 때마다 임대 상태, 수신자, 만료, grant revision, consent revision, 목적, 열린 incident, 기기 소속을 다시 검사함. 보호자나 수신자가 회수하면 즉시 REVOKED 상태가 됨.
- 암호화: 정밀 위치는 AES-256-GCM으로 봉인하고 `payloadRef`를 AAD로 묶음(`mec-state.mjs`). 열람 때 `payloadHash`를 다시 대조하고, 열람 결과는 최대 5초 뒤 만료되는 `readExpiresAt`을 가짐.
- 최소 수집(data minimization): 외부로 나가는 값은 `encrypted-location-reference`(참조, hash, 출처 유형, 관측 시각, 만료)뿐임. 이번 프런트와 guard 감사 기록도 originator digest, 본문 SHA-256, 경로, query key 이름만 남김.
- 전송 보호: CSE 진입 HTTP와 MQTT 모두 TLS 1.3과 클라이언트 인증서를 요구함.
- 기존 실측: `docs/verification-evidence/2026-11-11/location-privacy-real-cse.json` PASS.

## 한계

- 실행 범위는 개발 PC 1대의 loopback 경로임. Pi Gateway와 키링 실물 검증은 장비, 인증서, endpoint, 시험 receipt를 갖춘 별도 실행이 필요함.
- nginx 형제 템플릿은 Pi 경로용 설계본이며, 이 PC에는 nginx가 없어 실행 기준은 Node 프런트임. nginx 경로는 CN만 매핑하므로 SAN URI와 지문 고정이 필요하면 Node 프런트를 사용함.
- CSE에서 AE로 가는 알림은 loopback HTTP 수신기로 받음. 알림 경로의 TLS 적용은 다음 단계 작업임.
- Mosquitto ACL 파일은 브로커 시작 때 생성함. 회수는 guard가 즉시 처리하고, ACL 파일 갱신은 브로커 재시작이나 Linux SIGHUP 때 반영됨.
- CSE HTTP 포트는 127.0.0.1에 묶여 있음. 운영 배치에서는 이 포트를 컨테이너 내부망이나 로컬 소켓으로 한정해 프런트가 유일한 진입점이 되도록 구성해야 함.
- 인증서 회수는 바인딩 표로 처리함. CRL 적용은 프런트의 `tls.crl` 옵션으로 준비되어 있고 OCSP 연동은 별도 작업이 필요함.
- FORWARDED 감사 행은 응답 완료 뒤 기록함. 감사 저장 실패 시 요청을 막는 구성이 필요하면 전달 전 기록 단계를 추가해야 함.

## 재현 절차

```bash
export MOBIUS4_ROOT="<Mobius4 4.24.5 checkout>"
node pc-mobius/scripts/run-acp-mtls-real.mjs              # 기본 provider 2개, Mosquitto가 있으면 MQTT 포함
node pc-mobius/scripts/run-acp-mtls-real.mjs --skip-mqtt  # HTTP 경로만
npm --prefix pc-mobius test
```

필요 조건: `.local/postgres/connection.json`, PATH의 `openssl`(또는 `OPENSSL`), MQTT 시험용 `mosquitto`(또는 `MOSQUITTO_EXE`). 인증서, 개인키, 바인딩 표, 감사 기록은 모두 `.local/acp-mtls/<run>/` 아래에 생성됨.
